# Актёры и Notion — замысел и состояние работ

Документ для того, кто продолжит разработку. Здесь замысел, принятые
с пользователем решения, устройство кода, что сделано и что осталось.
Правила разработки — общие для проекта: [CLAUDE.md](CLAUDE.md) и
[PLAN.md §12](PLAN.md#12-правила-разработки).

---

## 1. Зачем это нужно

Пользователь режет из фильмов и сериалов короткие отрезки для изучения
языка. Каждый отрезок подписывается репликой из субтитров. Двух вещей
не хватало:

1. **Кто говорит.** К отрезку нужно приписать актёра — имя по-русски
   и роль: `Майкл Джонстон (Bear)`. Список актёров берётся из базы фильмов
   TMDB по названию открытого файла.
2. **Куда это девать.** Готовые отрезки должны уезжать в Notion — в базу,
   устроенную так же, как база-образец в рабочем пространстве пользователя.
   Оттуда их подхватывает его собственный синхронизатор
   (`C:\PITH\Development\NOTION_PITH`, Node.js).

---

## 2. Решения, принятые с пользователем

Спрашивал прямо; здесь ответы, чтобы не переспрашивать.

### Актёры

| Вопрос | Решение |
|---|---|
| Ключ TMDB | Пользователь вводит его сам — поле прямо в окне актёров, хранится в `settings.json`. В поставку не входит |
| Сколько актёров | 50 (состав приходит одним запросом, предел — только длина списка) |
| Выбор картины | Первое совпадение поиска. Диалога выбора нет |
| Куда пишется актёр | Отдельным полем закладки. **Не** в название: название идёт в имя вырезанного файла |
| Где виден и правится | Только в диалоге переименования — второе поле. В списке отрезков не показывается |
| Сколько актёров у закладки | Один. Новый выбор заменяет прежнего |
| Куда попадает выбор | Закладке под курсором, а если её там нет — **ближайшей по времени**. Окно сообщает, какой именно |
| Язык роли | Как отдала база (обычно английский). Имя актёра — по-русски, если база знает |
| Окно | Отдельное, поверх всех окон, клавиша `A`, положение и открытость запоминаются |

### Notion

| Вопрос | Решение |
|---|---|
| Токен и страницы | Вводятся в отдельном окне интеграций внутри плеера. Токен подставить из `config.json` синхронизатора как значение по умолчанию |
| База-образец | Страница `DIFF`, ссылку даёт пользователь: `https://app.notion.com/p/DIFF-330b5e5392878039ab95ef453be3db03`. Только читается |
| Куда выгружаем | **Одна база на все картины** — страница `Cards prod` (`3bab5e539287804d83b7f934db040493`), копию образца пользователь сделал сам кнопкой «Duplicate». Картины различаются полем `FILM NAME` |
| Почему так | Копии страницы в API нет ни в каком виде (см. §3). Ручная копия — единственный способ сохранить виды, фильтры и оформление; делается один раз, а не на каждую картину |
| Что выгружаем | Только активный список отрезков |
| Заголовок строки | **Сквозной** номер по базе: новая выгрузка продолжает счёт, а не начинает заново. Одинаковые реплики в `" ENG"` при этом допустимы — совпадать не должны только номера |
| Название картины | `Фильм: Название` либо `Сериал: Название`, по умолчанию сериал. Пусто — `Без названия` |
| Язык названия | Переключатель «Рус / Англ» в окне выгрузки. Русское берётся из состава картины (`cast.json`, база отдаёт его вместе с актёрами), английское — из имени файла. Отдельных запросов не нужно; состав не запрашивали — «Рус» не нажимается |
| Порядок строк | Держится на числовом поле `NUM`: плеер заводит его в базе сам и пишет туда номер. Вид в Notion сортировать **по `NUM` по возрастанию** — это единственный ручной шаг, API виды не настраивает |
| Нет актёра | Не ошибка. Поле не заполняется, в отчёте отмечается |

## 3. Что выяснилось на живых данных

Это стоило времени — не переоткрывайте заново.

- **Имена актёров TMDB отдаёт по-русски**, если просить `language=ru-RU`.
  Роли — почти всегда по-английски. Отдельный запрос за русским именем
  (`/person/{id}` → `also_known_as`) в крейте есть, но в приложении не нужен:
  проверено на `Obsession.2025`, имена пришли готовыми.
- **Notion не умеет дублировать базу через API.** Только прочитать свойства
  и создать новую с такими же. Виды, сортировки, фильтры и оформление
  не переносятся — API их не отдаёт.
- **Схема образца** (база «Text sourse» внутри страницы `DIFF`): 17 свойств.
  Заголовок назван **пустой строкой**, у английской реплики имя
  **с пробелом в начале** — `" ENG"`. `ACTOR` — это `multi_select`,
  а не текст. `FILM NAME` — текстовое поле **в каждой строке**.
  Пять формул, которые переносятся вместе с выражением, и `Last edited time`,
  которое Notion ведёт сам и задавать не даёт.
- **Запятая в имени варианта `multi_select` недопустима** — она делит
  варианты. Заменяется пробелом.
- **Текст длиннее 2000 знаков** Notion отвергает — реплика обрезается.
- **Разбор ссылок Notion**: в `DIFF-330b5e…` буквы `FF` из слова «DIFF» тоже
  шестнадцатеричные. Номер — это **последние 32 знака** куска, а не первые
  найденные.
- **Отказ Notion объясняет словами** — «page not shared with integration»
  и подобное лежит в теле ответа. Клиент `ureq` по умолчанию превращает код
  состояния в ошибку и тело теряет, поэтому у агента стоит
  `http_status_as_error(false)`, а код разбирается своими руками
  (`client.rs::read_answer`). Без этого пользователь видел один код.
- **Формулы ссылаются на свойства номерами, а не именами.** Внутри
  выражения стоит `{{notion:block_property:%7BU%3Fu:…}}`, где `%7BU%3Fu` —
  номер свойства **той** базы. Скопированное дословно выражение в новой
  базе ссылается в пустоту, и все формулы считают пусто. Лечилось вторым
  заходом: после создания базы её свойства перечитывались, номера
  сопоставлялись по именам и формулы отправлялись `PATCH`-ем. Кода этого
  больше нет — база одна и сделана руками, создавать её плеер перестал
  (`schema.rs`, `create_database`, `link_formulas` удалены). Понадобится
  снова — смотреть в истории `git`.
- **Служебные свойства Notion принимает** — `last_edited_time`,
  `created_time`, `created_by`, `last_edited_by`, `unique_id` и даже
  `status` создаются через API (проверено запросами). Прежнее «Notion
  ведёт их сам и задавать не даёт» оказалось неверным: из-за него в копии
  не было `Last edited time`, а на него ссылалась формула `ACTIVE`.
  Не переносятся только `relation` и `rollup` — их не на что нацелить.
- **Значок и встроенность базы** задаются при создании (`icon`,
  `is_inline`). Без них копия открывалась отдельной страницей без значка
  и на образец была не похожа.
- **Копии страницы через API нет — проверено живьём** (13.08.2026, токен
  синхронизатора, страница `DIFF`). Три способа, три отказа:
  `POST /v1/blocks/{id}/duplicate` и `POST /v1/pages/{id}/duplicate` —
  `invalid_request_url` (таких путей нет), `POST /v1/pages` с полем
  `duplicate_from` — `validation_error: body.duplicate_from should be not
  present`. То же самое под версией `2025-09-03`. Кнопка «Duplicate»
  в интерфейсе Notion зовёт внутренний `api/v3` с куком браузера, а не
  токеном интеграции. Отсюда: «скопировать `DIFF` целиком и заполнить копию»
  плеер сам сделать не может — только через ручной дубль в Notion.
- **Свежая версия API (`2025-09-03`) видов тоже не отдаёт.** У базы
  появилось поле `data_sources` (у образца один источник — «Text sourse»),
  но в ответе `GET /v1/data_sources/{id}` слова `view` нет вовсе.
- **В базе образца одна строка**, и в её теле 4 блока из 5 приходят как
  `unsupported` — тело строки не копируется даже поблочно.
- **Виды перенести нельзя вовсе.** API не отдаёт ни колонок вида, ни
  сортировок, фильтров и группировок — их просто нет в ответе. Поэтому
  в копии видны **все** свойства, а в образце вид часть из них прячет.
  Это не ошибка выгрузки, а предел API: вид копии настраивается руками
  один раз.
- **Тело строк не копируется**: в образце внутри карточки лежат блоки
  (в ответе они `unsupported`), у новых строк тело пустое.
- **Строка-образец несёт значения, и их нужно наследовать.** В базе `DIFF`
  одна строка `CARD (1)`, и в ней проставлено: `STATUS = Созданы`,
  `TRANSCRIPTION SENTENCE = ////////////////`. `STATUS` синхронизатору
  не безразличен — обратная синхронизация смотрит на `STATUS != "Созданы"`
  (`notion-sync.js:284`). Раньше плеер создавал строки с нуля и эти значения
  терял. Теперь значения строки образца читаются (`client::first_row`),
  пересобираются в пригодный для записи вид (`defaults::from_row`:
  варианты списков по имени, а не по номеру; текст без оформления
  и `plain_text`) и ложатся в основание каждой новой строки — свои поля
  плеер кладёт поверх.
- **Синхронизатор пользователя копий не делает.** В `NOTION_PITH` к Notion
  идут только `POST /databases/{id}/query`, `GET /pages`, `GET /blocks`,
  `POST /pages` с `parent.database_id` (это строка, не страница)
  и `PATCH /pages`. Ни `POST /databases`, ни создания страниц там нет:
  базы фильмов к его приходу уже существуют.
- **TMDB у провайдера пользователя разрешается в `127.0.0.1`.** Проверено:
  `Resolve-DnsName api.themoviedb.org` через домашний DNS отдаёт `127.0.0.1`,
  и то же для `image.tmdb.org`. Слушать там некому, поэтому запрос напрямую
  кончается «io: Connection refused» — при работающей сети и верном ключе.
  Доступ идёт через прокси `127.0.0.1:10809`, который VPN-клиент прописывает
  **в настройки Windows** (`ProxyEnable`, `ProxyServer`). `ureq` читает
  прокси только из `HTTP_PROXY`/`HTTPS_PROXY`, а у окна, запущенного
  из проводника, переменных нет — из консоли те же запросы проходили,
  и это сбивало с толку. Теперь при запуске плеер читает прокси системы
  (`pith-app/src/net.rs`) и называет его обоим сетевым крейтам
  (`pith_tmdb::use_proxy`, `pith_notion::use_proxy`); переменные окружения
  главнее — если они есть, не вмешиваемся, иначе потеряли бы `NO_PROXY`.
  **Notion при этом открывается напрямую**, поэтому выгрузка работала,
  а актёры нет: похоже на поломку в плеере, а причина в сети.
- **Новый клиент на каждый запрос стоил дороже самого запроса.** У `ureq`
  свой пул соединений, и заведённый заново клиент каждый раз открывает TCP
  и пожимает руки по TLS — через прокси это больше секунды. Замер на живом
  Notion: было **1,71 с** на строку и 5,75 с подготовки, стало **0,64 с**
  и 3,07 с. Прогноз на тридцать закладок — 57 с против 22 с. Клиент теперь
  один на процесс (`net.rs`, `OnceLock`), и так же у базы фильмов: потоки
  фотографий разбирают тот же пул.
- **Последний номер спрашиваем одним запросом.** `POST /databases/{id}/query`
  с `sorts: [{timestamp: created_time, direction: descending}]` и
  `page_size: 5` — проверено, работает. Строки создаются по возрастанию,
  значит наибольший номер у одной из последних созданных. Обход всей базы
  стоил бы запрос на каждую сотню строк: на девятистах — девять запросов
  и семь секунд перед каждой выгрузкой. Пять берём с запасом, на случай
  строк, добавленных руками не по порядку.
- **Подготовка идёт заранее, пока открыт вопрос.** Три запроса (номер базы,
  строка образца, последний номер) — это три-четыре секунды, и раньше они
  ждали нажатия «Выгрузить». Теперь они уходят на первом кадре окна
  (`prefetch_export`), пока человек выбирает название и вид, а `export`
  получает готовый `Prepared`. Не успело или не вышло — выгрузка спросит
  сама, в своём потоке: `run` принимает `Option<Prepared>`. Побочная польза:
  отказ доступа виден в окне **до** нажатия, а не после.
- **Сайт словаря терпит три потока разом.** Замер на живых страницах,
  слова каждый раз свежие: 12 слов одним потоком с паузой 200 мс — 3,5 с,
  тремя потоками с той же паузой — 2,8 с (пауза сама стала пределом),
  тремя потоками **без** паузы — 1,7 с. На длинной череде в 24 слова —
  2,7 с, и все 24 нашлись в первом словаре: ни одного отказа. Отсюда разное
  устройство двух путей: в выгрузке человек ждёт, и там три потока без
  выдержки; в разогреве во время просмотра не ждёт никто, и там один поток
  с паузой — вежливость к чужому бесплатному сайту.
- **Плеера фоновый разогрев не касается.** Замер на 4К (`Obsession.2025`,
  кадр 3840×2160): время кадра 16,7 мс (~60 к/с) и с разогревом, и без;
  83 слова пятнадцати закладок легли в память за 40 секунд просмотра.
  Причина простая: поток занят ожиданием сети, а не счётом. Чтобы так
  и оставалось, интерфейс он не будит, а в файл пишет раз за кадр,
  сколько бы слов ни подоспело.
- **У сокращений апостроф снимать нельзя.** `we're` без него превращается
  в `were`, `won't` в `wont`, `can't` в `cant` — это другие слова, и первый
  словарь честно отдаёт их транскрипцию. Ошибка тихая: поле заполнено,
  только неверно. Поэтому у слов с апострофом первым спрашивается **второй**
  словарь: он знает точную форму и зовёт её через дефис — `we're` живёт
  по адресу `we-re`. Замер: `we're` давало `|wɜːr|` (это `were`), стало
  `|wɪr|`.
- **В закрывающем теге тоже есть косая черта.** Запись Cambridge обрамлена
  косыми (`/…/`), и разбор «до следующей косой» обрывался на `</span>`:
  `ˈhæv.<span>ə</span>nt` давало `ˈhæv.ə`. Разметку приходится читать
  с оглядкой на теги и искать закрывающую косую **вне** их.
- **Повторов с паузами у первого словаря больше нет.** В готовой системе
  слово, которого сайт не отдал, спрашивалось четырежды с паузами 5, 8 и 8
  секунд. С общим клиентом ограничитель не появляется вовсе, а цена этих
  повторов оказалась велика: сайт отвечает страницей без транскрипции
  и на сокращения вроде `havent`, и каждое такое слово стоило **21 секунду**
  ожидания на пустом месте — при двух закладках выгрузка вставала на минуту.
  Теперь по одному запросу в каждый словарь. Слово без транскрипции в память
  не попадает, так что следующая выгрузка попробует его заново.
- **Незнакомое слово первый словарь отдаёт кодом `404`, а ограничитель
  частоты — кодом `200` с пустой страницей.** Различать их обязательно:
  на `404` идти ко второму словарю сразу, а на заглушку — ждать и повторять.
  Готовая система пользователя этого не различала и на каждое незнакомое
  слово тратила четыре попытки с паузами. Отсюда и `http_status_as_error(false)`
  у клиента: иначе код теряется.
- **Порядок обхода словарей не «первый, потом второй», а хитрее.** Первый
  словарь под ограничителем частоты отвечает заглушкой, и по ней не отличить
  занятый сервер от отсутствующего слова. Ждать четыре попытки (это двадцать
  секунд) незачем: второй словарь отвечает меньше чем за секунду и даёт ту же
  американскую транскрипцию. Поэтому: один запрос к первому → второй словарь
  → и только если оба молчат, повторы к первому с паузами. Замер на живых
  сайтах: слово `selfie` под ограничителем стоило **24 с**, этим порядком —
  **1,2 с**; тройка слов 28 с → 5,3 с.
- **Англо-русская страница Cambridge транскрипции не содержит вовсе** —
  проверено запросом: слова `where` там не найти ни в одном виде. Нужен
  английский словарь: `/dictionary/english/{слово}`.
- **Разметка Cambridge: у класса блока пробел в конце** (`class="us dpron-i "`),
  и запись рассыпана по нескольким `span` — в `weər` часть `r` лежит отдельным
  `span class="sp dsp"`. Поэтому берём всё между косыми и снимаем разметку
  без пробелов. Первый разбор промахнулся именно на этом пробеле.
- **Слово стоит около секунды, и это главная цена транскрипции.** Первый
  словарь требует паузы 1,2 с между запросами. Спасает счёт **по словам,
  а не по репликам**: «you», «to», «the» встречаются в каждой второй реплике,
  и каждое слово спрашивается один раз на всю выгрузку, а потом ложится
  в `transcriptions.json` и больше не спрашивается никогда.
- **Числовое поле `NUM` развязало порядок и скорость.** Пока номер жил
  только в текстовом заголовке, порядок строк держался на порядке создания:
  по тексту сортировать нельзя («10» встаёт перед «2»), а значит и писать
  строки в несколько потоков нельзя. Теперь номер идёт ещё и числом,
  вид сортируется по нему, и кто первым доехал — неважно. Поле плеер
  добавляет сам при подготовке (`ensure_number_property`, `PATCH` по базе):
  проверено живьём — свойство появилось (`type: number`), строки 23–31
  сортируются по нему по возрастанию. Нет поля — строки всё равно уйдут,
  только без числа: свойства, которого в базе нет, Notion не принимает,
  и `row::properties` его тогда не отправляет.
- **Строки пишутся в три потока** (`writer.rs`). Три, а не больше: у Notion
  предел около трёх запросов в секунду, дальше `429`. Отказ по частоте
  переживается повтором с удвоением задержки, прочие отказы повторять
  незачем. Замер: строка стоила 0,78 с, стала **0,41 с** — ускорение
  вдвое, а не втрое, потому что предел частоты никуда не делся. Тридцать
  закладок — около 12 с видимого ожидания.
- **Старые строки остаются с пустым `NUM`** — они созданы до появления
  поля. При сортировке по возрастанию Notion ставит пустые в конец.
  Заполнять их плеер не берётся: это чужие данные.
- **Замеры на живом Notion сильно шумят.** Пять строк подряд: 5,99 / 7,88 /
  6,89 с — разброс четверть от величины, потому что трафик идёт через
  прокси. Судить об ускорении по одному прогону нельзя, нужно три.
- **Порядок строк в базе — это порядок создания, и вид его только
  показывает.** API не сортирует и вида не касается. Отсюда правило: строки
  отправляются **по порядку**, от первой к последней, а вид в Notion
  сортируется по времени создания по возрастанию. Тогда номера читаются
  сверху вниз и внутри выгрузки, и между выгрузками. Обратная отправка
  (была) выпрямляет одну выгрузку, но следующая ложится поверх прежних
  с большими номерами, и столбец читается 6, 7, 8, 3, 4, 5 — при виде
  «новые сверху» монотонного столбца не получить вовсе, номера ведь растут.
- **Нумерация в базе сквозная, и это надо спрашивать у Notion.** База одна
  на все картины, поэтому перед выгрузкой читается наибольший номер среди
  заголовков (`client::max_number`, страницами по сотне) и счёт продолжается
  с него. Заголовки, которые числом не читаются, пропускаются — у образца
  это `CARD (1)`. Проверено на боевой базе: в ней было максимум 2, три новые
  строки легли 3, 4, 5. Не вышло спросить — начинаем с единицы: строки
  важнее номеров, а совпавший номер ничего не ломает.
- **Описание дочернего окна собирается каждый кадр, и egui приказывает окну
  всё, что в нём изменилось.** Если каждый кадр называть размер и положение
  (а мы их же и отслеживаем), окно спорит с пользователем: тот тянет за край,
  а плеер возвращает сохранённый размер — окно дёргается, и особенно заметно
  после разворота на весь экран и возврата обратно. Лечится тем, что место
  называется **один раз при показе** (`child_window::place` с признаком
  `placed`), а дальше размером распоряжается только пользователь.
- **`ScrollArea::show_rows` добавляет отступ между строками сам** и просит
  высоту «без отступа». Свой `add_space` сверху ломал счёт: область
  прокрутки считала высоту списка по одному отступу, а строки занимали два,
  и список плыл под полосой прокрутки.
- **Кадр закрытия обрывается до отрисовки окон** (`handle_close_request`
  возвращает `true`, и `ui` выходит сразу), поэтому дочерние окна просьбу
  закрыться при выходе не читают, и открытость окна актёров в настройках
  не портится. Проверено: закрыли плеер с открытым окном актёров —
  в `settings.json` осталось `actors_window_open: true`, и при следующем
  запуске окно появилось там же и того же размера.
- **Чёрный прямоугольник вместо крупной фотографии** — следствие того же:
  мелкие (`w185`) уже лежали в кэше на диске и рисовались, а крупная
  (`w500`) — новая загрузка, и она не проходила. Теперь, пока крупной нет,
  показывается растянутая мелкая и надпись «Загружаю…»: хуже качеством,
  зато видно, что происходит.
- **Ответ из потока сам интерфейс не будит.** egui рисует кадр только по
  событию, и готовый ответ лежал в канале до ближайшего движения мышью.
  Рабочий поток берёт с собой `egui::Context` и в конце зовёт
  `request_repaint()` — так сделано у состава, фотографий, проверки доступа
  и выгрузки. Таймеров-опросов при этом не появилось.

**Направление зависимостей:** `pith-app` → `pith-tmdb` / `pith-notion` →
ничего из проекта. Крейты знают только про свою чужую систему, ни про окна,
ни про хранение (PLAN.md §12.4).

**Сеть — всегда в отдельном потоке.** Запрос уходит в `std::thread::spawn`,
ответ забирается из канала в кадре (`poll_cast`). Правило проекта: ничего
блокирующего в потоке интерфейса.

### Данные

- `settings.json` — `tmdb_key`, `actors_window`, `actors_window_open`,
  `export_window` и `notion` (`token`, `work_page`, `template_page`).
  Место дочерних окон пишется не на каждое движение мышью, а при закрытии
  окна и выходе из плеера: файл настроек — не журнал. Ссылки хранятся
  целиком, как их принёс пользователь: номер из них достаётся при
  обращении. `work_page` — страница с рабочей базой, `template_page` —
  `DIFF`, откуда берётся заготовка строки. Обе подставляются по умолчанию.
- `cast.json` — версия формата 1, составы по ключу «имя файла без расширения».
- `bookmarks.json` — у закладки появилось `actor: Option<String>`
  с `#[serde(default)]`: старые файлы читаются без миграции.
- `photos/` — кэш фотографий, имя файла берётся из пути TMDB.

## 6. Осталось

Ничего обязательного. Что стоит сделать, когда дойдут руки:

- **Проверить, что синхронизатор подхватывает** рабочую базу как свою
  (`C:\PITH\Development\NOTION_PITH`). Он обходит базы под страницей
  карточек — значит, `Cards prod` должна лежать там, где он смотрит,
  а `CARDS_PAGE_ID` в его `config.json` указывает на другую страницу.
- **Порядок свойств в базе не задаётся.** Пока рабочая база одна и сделана
  руками, это не важно. Если снова понадобится создавать базы из плеера —
  помнить, что `serde_json::Map` без `preserve_order` сортирует ключи
  по алфавиту, а нужного порядка колонок API не отдаёт вовсе: это
  настройка вида.
- **Раскрытие фотографии по наведению убрано.** Было: курсор постоял
  на снимке — картинка раскрылась. На живом списке это мигало: пока ведёшь
  мышь к нужной строке, картинка выскакивает и гаснет на каждой соседней.
  Осталось только нажатие. Если вернётесь к этой мысли — раскрывать надо
  не поверх списка, а рядом с курсором, и гасить без перерисовки всего окна.
- **Положение окна интеграций** не запоминается: у актёров и выгрузки
  теперь запоминается (`app/child_window.rs`), у интеграций — нет.
  Делается тремя строками по образцу соседей.
- **Выгрузка всех списков сразу**: сейчас уходит только активный.
- **Склейку транскрипции с выгрузкой живьём не проверяли.** Каждое звено
  проверено по отдельности — словари на живых сайтах (`dict_probe`), поле
  Notion тестами, сама выгрузка на боевой базе (`export_probe`), — но полный
  проход «панель → окно → транскрипция → строки в Notion» ни разу не сделан:
  панель отрезков в этих сеансах не открывалась язычком, нажатия шли мимо.
  Проверять руками: открыть панель, значок Notion, переключатель
  «Транскрипция реплик» и посмотреть на `TRANSCRIPTION SENTENCE` в базе.
- **Живьём не сняты** два окна: выгрузки (в отдельном окне) и интеграций
  после переработки. Оба собираются и устроены как окно актёров, которое
  снято, но глазами их никто не видел. Панель отрезков в этом сеансе
  язычком не открывалась — нажатия в неё шли мимо, и до кнопки Notion
  скрипт не дошёл.

Живые проверки интерфейса — скриптами по образцу `scripts/ui_probe.ps1`:
запустить плеер, найти окно по заголовку, нажать клавишу, снять окно,
сверить с ожидаемым. Так проверялись окно актёров, привязка и фотографии.

`-ItemY` у проверки интеграций — высота пункта меню в окне: она зависит
от состава меню, и берётся со снимка `-MenuOnly`.

Про `export_test.ps1`, если он опять начнёт мазать по кнопкам:

- Кнопки панели стоят **одной** строкой: «Вырезать отрезки», за ней значок
  выгрузки и значок очистки, оба шириной 38 у правого края. Скрипт целится
  в `Right − 85` по горизонтали и `Bottom − 82` по вертикали; поменяется
  разметка — поменять и эти числа.
- Окно выгрузки — отдельное окно системы, и `MainWindowHandle` указывает
  не на него. Ищется по заголовку: `Get-PithChildRect $proc "Выгрузка
  в Notion"` (в `ui_probe.ps1`).
- **Скриптам нужна метка UTF-8 в начале файла.** PowerShell 5.1 без неё
  читает файл в кодировке системы, и русские строки внутри скрипта
  превращаются в кракозябры — в песочницу уезжает список с именем
  «РћСЃРЅРѕРІРЅРѕР№» вместо «Основной».
