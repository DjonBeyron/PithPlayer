# Pith Player v5.0.0

Плеер на Rust: движок **libmpv** (render API, OpenGL), интерфейс **egui/eframe**.
Перенос с C#/WinForms/LibVLC версии, лежащей в `C:\PITH\Source\Pith player`.

Полный план и карта переноса: [PLAN.md](PLAN.md).
Полные правила разработки: [PLAN.md, раздел 12](PLAN.md#12-правила-разработки).

---

## Обязательные правила

### Язык
- **Отвечать пользователю только на русском.** Всегда.
- Комментарии в коде — на русском. Идентификаторы и имена файлов — на английском.
- Сообщения коммитов — на русском.

### Размер файлов — жёсткий предел
- **Максимум 400 строк на файл исходного кода.** Не пожелание, а правило.
- Файл дорос до предела — разбить немедленно, а не потом.
- Функция — до 50 строк, вложенность — до 3 уровней.
- Исключение: `PLAN.md` и прочая документация.

Проверять перед каждым коммитом:

```bash
find crates -name "*.rs" -exec wc -l {} + | awk '$1 > 400 {print "ПРЕВЫШЕНИЕ:", $2, $1}'
```

### Надёжность
- **Никаких `unwrap()` / `expect()` в рабочем коде** — только `Result`
  (`thiserror` в крейтах, `anyhow` в `pith-app`). В тестах разрешено.
- Битый файл или отсутствующий кодек — сообщение пользователю, не паника.
- Нет `ffmpeg.exe` — отключается только нарезка, плеер продолжает работать.

### Архитектура
- Зависимости в одну сторону: `pith-store` ← `pith-mpv` / `pith-subs` / `pith-fragments` ← `pith-app`.
- **UI не обращается к libmpv напрямую** — только через `pith-mpv`.
- Состояние приложения — в одном месте (`app.rs`), не размазано по компонентам.
- **Никаких таймеров-опросов.** Только события mpv и `observe_property`.
  «Подождать 800 мс и попробовать ещё раз» — признак ошибки проектирования.
- Блокирующие операции — вне UI-потока.

### Гигиена
- Мёртвый код удалять, а не комментировать.
- Магические числа — только именованными константами.
- `println!` / `dbg!` запрещены — только `tracing`.

Перед коммитом:

```bash
cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test
```

### Данные пользователя
- В каждом JSON — поле `version`; миграции без потерь, старый файл в `.bak`.
- Запись атомарная: временный файл → `rename`. Закладки терять нельзя.

### Процесс
- Каждый этап завершается работающим приложением; `main` всегда собирается.
- Коммиты маленькие, по одной задаче.
- Новая зависимость — с обоснованием.
- Оптимизация только после замера.

## Особые требования

### Нарезка отрезков — это перепаковка контейнера
Режим по умолчанию: `-c copy`, без перекодирования. На опорный кадр встаёт
сам FFmpeg — своего выравнивания через `ffprobe` не делаем: когда просят время
ровно опорного кадра, FFmpeg отходит назад ещё на один, и отрезок выходит
длиннее заказанного (замер на 4К: 20,2 с вместо 18). Контейнер выбирается
автоматически (MP4 / MKV / MOV) по совместимости с исходными кодеками.
Подробно — PLAN.md §6.4.

Обязательно сохранить из v4: `-map 0:v:0` (только основной видеопоток, без обложек)
и `-avoid_negative_ts make_zero`. При `-c copy` **не ставить второй `-ss` после `-i`** —
именно он даёт отрицательные timestamps и чёрные кадры.

Когда звук приводится к AAC, видео копируется, а звук перекодируется — и FFmpeg
обходится с ними по-разному: копию начинает с опорного кадра перед меткой, а звук
обрезает ровно по метке. Отрезок выходил с двумя секундами тишины в начале.
Лечится тремя ключами вместе: `-noaccurate_seek`, `-copyts` и конец через `-to`,
а не `-t`. Главы исходника в отрезок не переносим (`-map_chapters -1 -dn`):
FFmpeg пишет их дорожкой длиной во весь фильм.
`-movflags +faststart` по умолчанию не ставить — лишний проход по файлу.

Скорость: `ffprobe` исходника вызывать **один раз** при открытии видео и кэшировать
(в v4 он звался заново на каждую закладку), очередь фрагментов обрабатывать
параллельно (3–4 процесса на SSD, последовательно на HDD).

Запасной режим с перекодированием (`libx264 -preset ultrafast -crf 18` + `aac`,
двойной `-ss`) переносить из v4 дословно — это выстраданное решение.

### Опция `vo=libmpv` обязательна
Без неё mpv открывает своё окно вывода поверх нашего: перехватывает клавиатуру,
становится главным окном процесса и подвешивает закрытие. Проверяется по числу
видимых окон процесса — должно быть ровно одно, «Pith Player».

### Окно подстраивается под форму видео
Вертикальное видео открывается вертикальным окном, без чёрных полос.
Размеры брать из `video-params/dw` и `video-params/dh` — **не** из `w`/`h`,
иначе видео с телефона (`rotate=90` в метаданных) откроется лёжа.

Реализация максимально простая: три шага при открытии файла, без хитростей.
Любое сомнение — **окно не трогаем**, mpv покажет кадр с чёрными полями.
Это штатное поведение, а не ошибка. Не усложнять. Подробно — PLAN.md §6.12.
