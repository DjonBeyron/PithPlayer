# Pith Player v5.0.0 — план переноса на Rust

Документ описывает перенос плеера **Pith Player** (C# / WinForms / LibVLC, ~43 000 строк)
на Rust с движком **libmpv** и интерфейсом **egui**.

- Исходник: `C:\PITH\Source\Pith player`
- Новый проект: `C:\PITH\Source\Pith_Player v5.0.0`
- Дата составления: 31.07.2026

---

## 1. Цель и критерии успеха

### Цель
Получить плеер, который делает всё, что делает текущий, но:
- запускается за доли секунды вместо секунд;
- тянет 4К/HDR/HEVC/AV1 без просадок;
- не имеет «слоёного пирога» из 30+ таймеров и layered-окон;
- собирается в один `.exe` без .NET-рантайма.

### Критерии приёмки (проверяем замерами на этапе 0 и в конце)

| Показатель | Сейчас (C#/VLC) | Цель (Rust/mpv) |
|---|---|---|
| Холодный старт до первого кадра | несколько секунд | **< 400 мс** |
| Seek на 4К HEVC | заметная задержка | **< 150 мс** |
| CPU при 4К с hwdec | — замерить | **< 10 %** на среднем ПК |
| RAM в покое с видео | ~300–500 МБ | **< 150 МБ** |
| Размер дистрибутива | .NET + VLC-плагины | `.exe` + `libmpv.dll` + `ffmpeg.exe` |
| Форматы | всё, что умеет VLC | всё, что умеет FFmpeg (шире) |

## 2. Технологический стек

| Слой | Выбор | Почему |
|---|---|---|
| Видео-движок | **libmpv** (mpv 0.39+/0.40+) | Быстрейший конвейер: FFmpeg + собственный GPU-рендерер, лучший hwdec, зрелые субтитры (libass) |
| Rust-биндинг | **`libmpv2`** (crate) | Актуальный форк `libmpv-rs`, поддерживает Windows, есть render API |
| Вывод кадра | **mpv render API** (OpenGL) | mpv рисует в наш FBO → текстура → композитим с UI в одном кадре |
| GUI | **`eframe` / `egui`** (backend `glow`) | Immediate-mode, тот же GL-контекст, что и mpv; идеально для оверлеев субтитров |
| Нарезка отрезков | **FFmpeg CLI** (внешний `ffmpeg.exe`) | Текущая логика уже правильная — переносим 1:1, меняется только язык обвязки |
| Парсинг субтитров | **чистый Rust** (`nom` или `regex`) | SRT / ASS / SSA / VTT — простые форматы, внешних зависимостей не надо |
| Сериализация | **`serde` + `serde_json`** | `bookmarks.json`, `watch_positions.json`, `settings.json` |
| Логи | **`tracing`** + `tracing-appender` | Замена `SubtitleLogger` / `Debug.WriteLine` |
| Асинхронность | **`tokio`** (только для FFmpeg-процессов и I/O) | UI остаётся синхронным (egui), тяжёлое — в фон |

### Внешние бинарники, которые кладём рядом с `.exe`
- `libmpv-2.dll` — сборка **shinchiro** (`mpv-dev-x86_64-*.7z` содержит `.dll`, `.lib` и заголовки)
- `ffmpeg.exe` + `ffprobe.exe` — для нарезки отрезков

## 3. Как устроен рендер-конвейер

```
                    ┌──────────────────────────────────────────┐
                    │            Одно окно (winit)             │
                    │  ┌────────────────────────────────────┐  │
   файл ──► libmpv ─┼─►│ FBO (видео-кадр, GPU)              │  │
   (декод, hwdec)   │  │      ▲                             │  │
                    │  │      │ mpv_render_context_render() │  │
                    │  └──────┼─────────────────────────────┘  │
                    │         │ текстура                       │
                    │  ┌──────┴─────────────────────────────┐  │
                    │  │ egui: субтитры, таймлайн, меню,    │  │
                    │  │       панель закладок, оверлеи     │  │
                    │  └────────────────────────────────────┘  │
                    └──────────────────────────────────────────┘
```

Ключевые моменты:

1. **`mpv_render_context_create`** с `MPV_RENDER_PARAM_API_TYPE = OPENGL` и
   `mpv_opengl_init_params { get_proc_address }` — адреса GL-функций берём у `glow`/`glutin`.
2. Каждый кадр: mpv рендерит в наш FBO (`mpv_opengl_fbo { fbo, w, h }`),
   затем egui рисует текстуру этого FBO как фон окна и поверх — весь UI.
3. **`mpv_render_context_set_update_callback`** → внутри вызываем
   `egui::Context::request_repaint()`. Никаких таймеров опроса — перерисовка ровно тогда,
   когда есть новый кадр.
4. **`mpv_set_wakeup_callback`** → события mpv (`FILE_LOADED`, `END_FILE`, `PROPERTY_CHANGE`)
   складываем в канал, разбираем в основном цикле.

> **Обязательная опция: `vo=libmpv`.** Без неё mpv открывает собственное окно
> вывода поверх нашего. Проверено на этапе 0: лишнее окно перехватывает
> клавиатуру (не работают пауза и перемотка), становится главным окном
> процесса и подвешивает закрытие приложения. Одна пропущенная строка
> давала сразу три несвязанных на вид симптома.
>
> Проверить можно по числу видимых окон процесса: их должно быть ровно одно,
> с заголовком «Pith Player». Окно класса `mpv` означает, что опция потерялась.
5. Свойства читаем через **`observe_property`** (push), а не опросом:
   `time-pos`, `duration`, `pause`, `volume`, `sub-text`, `secondary-sub-text`, `speed`, `aid`, `sid`.

> **Это заменяет** `_endCheckTimer` (50 мс), `scaleTimer`, `subtitleSelectionTimer`,
> `selectionTimer`, `delayTimer`, `notifyTimer`, `reportTimer` и остальные `Forms.Timer`
> из текущего кода.

### ⚠ Главный технический риск этапа 0: hwdec + OpenGL на Windows

При использовании OpenGL render API аппаратное декодирование работает так:

| Режим | Что происходит | Ожидание |
|---|---|---|
| `--hwdec=d3d11va` | zero-copy через расширение `WGL_NV_DX_interop2` | Лучший вариант; расширение есть у NVIDIA/Intel/AMD, но не гарантировано |
| `--hwdec=auto-copy` | декод на GPU, копия кадра обратно | Работает всегда, ~2–4 мс/кадр на 4К — приемлемо |
| `wid`-встраивание | mpv создаёт своё дочернее окно, полный zero-copy D3D11 | Запасной вариант; UI тогда — отдельное прозрачное окно поверх (как сейчас в WinForms) |

### ✅ Риск снят — результаты замеров (31.07.2026)

Замеры проведены на этапе 0. **Zero-copy работает**, запасные варианты не нужны.

- Файл: `Obsession.2025.2160p.WEB-DL.DDP5.1.DV.HDR.H.265.mkv` — 20 ГБ, 3840×2160,
  HEVC, Dolby Vision + HDR
- GPU: NVIDIA GeForce RTX 3070 Ti, контекст WGL
- Сборка: release, 20 секунд воспроизведения после выхода на установившийся режим

| Запрошено | Фактически применено | CPU (доля ядра) | RAM | До первого кадра |
|---|---|---:|---:|---:|
| **`zero-copy`** | **`d3d11va`** | **63,3 %** | **801 МБ** | 811 мс |
| `copy` | `d3d11va-copy` | 114,8 % | 912 МБ | 846 мс |
| `software` | `no` | 144,7 % | 1437 МБ | 826 мс |

Фактический режим читается из свойства mpv `hwdec-current` — без этой проверки
замеры недостоверны, потому что mpv молча откатывается при неудаче.

**Решение:** режим по умолчанию — `d3d11va,auto-copy`. Список задаёт порядок
предпочтения: на железе без `WGL_NV_DX_interop2` mpv сам возьмёт копирующий
режим. Встраивание через `wid` не понадобилось.

Время до первого кадра почти не зависит от режима — оно определяется разбором
20-гигабайтного контейнера, а не декодированием.

## 6. Ключевые механизмы в деталях

### 6.1 Движок: опции запуска mpv

```
--hwdec=d3d11va            # (или auto-copy — решаем по замерам этапа 0)
--vo=libmpv                # подразумевается render API
--profile=gpu-hq           # качественный скейлинг
--keep-open=yes            # не закрывать в конце файла
--force-window=no
--osc=no --osd-level=0     # свой интерфейс
--input-default-bindings=no --input-vo-keyboard=no   # свои хоткеи
--alang=eng,en             # аудио по умолчанию (из настроек)
--slang=eng,en             # субтитры по умолчанию (из настроек)
--sub-auto=fuzzy           # подхват внешних .srt рядом с видео
--audio-file-auto=fuzzy
--cache=yes --demuxer-max-bytes=256MiB   # плавность 4К
--volume-max=150
```

Кэширование: аналог текущих `file-caching=1000` / `disk-caching=1500` /
`network-caching=3000` — у mpv это `--cache-secs` и `--demuxer-readahead-secs`.

Спецкостыль для `.avi` из текущего кода (`demux=avformat`, `strict=-2`) **не нужен** —
mpv всегда использует libavformat.

### 6.2 Субтитры

**Источник текста.** mpv отдаёт текущую реплику в свойствах:
- `sub-text` — основные субтитры
- `secondary-sub-text` — вторые субтитры
- `sub-start` / `sub-end` — тайминги текущей реплики
- `sub-delay` / `secondary-sub-delay` — сдвиг

Подписываемся через `observe_property` — текст приходит push-ом ровно в момент смены реплики.
Никаких таймеров, никакого извлечения в `.srt` через FFmpeg, никаких синхронизаторов.

**Отрисовка.** Отключаем встроенный рендер (`sub-visibility=no`) и рисуем сами в egui —
это сохраняет текущий UX: перетаскивание, ресайз, выделение и копирование.

```rust
// ui/subtitles.rs — эскиз
egui::Area::new("main_sub")
    .movable(drag_enabled)
    .current_pos(state.main_sub_pos)
    .show(ctx, |ui| {
        let text = RichText::new(&state.sub_text)
            .size(state.main_sub_size)
            .color(state.main_sub_color)
            .background_color(state.main_sub_bg);
        let resp = ui.add(Label::new(text).sense(Sense::click_and_drag()));
        if resp.dragged() { state.main_sub_pos += resp.drag_delta(); }
        if resp.clicked()  { copy_to_clipboard(&state.sub_text); }
    });
```

Позиции/размеры обоих слоёв сохраняем в `settings.json`
(аналог `SubtitlePositionSettings.cs`).

**Копирование (клавиша `C`).** `arboard::Clipboard::set_text(sub_text)` + всплывающее
уведомление на egui с затуханием. Заменяет `SubtitleCopyHandler` + `SubtitleCopyOverlay` +
`FloatingCopyNotification` (~1 500 строк → ~80).

**Поиск по субтитрам.** Для поиска нужен весь текст, а не текущая реплика:
- внешний файл → парсим сами (`pith-subs/parse`);
- встроенная дорожка → один вызов `ffmpeg -i in.mkv -map 0:s:N -f srt -` и парсим stdout
  (одна операция вместо батчей/таймаутов/приоритетов текущего `IN_SubtitleExtractor`).

Результат — `Vec<SubtitleEntry { index, start, end, text }>`, поиск подстроки,
переход по клику. Плюс `sub-seek ±1` для перехода по репликам без индекса.

### 6.3 Выбор дорожек по умолчанию (по тегам)

Текущая система тегов из `SubtitlePrioritySettings.ini` — ценная и переносится как есть:

```
[MainSubtitles]   Enabled=true   Tags=sdh,english,eng,full,complete
[SecondarySubtitles] Enabled=false Tags=russian,rus,ru,full,forced
[Processing] Simultaneous=true SkipUnmatchedTracks=false
[Blacklist] Tags=
```

Алгоритм в `pith-mpv/tracks.rs`:
1. По событию `FILE_LOADED` читаем `track-list` (сразу полный и достоверный —
   в отличие от VLC, где приходилось ждать таймерами 800–1200 мс и делать 3 попытки).
2. Считаем приоритет каждой дорожки по тегам (порт `CalculateTrackPriority`,
   учитываем `title`, `lang`, флаги `forced`/`default`/`hearing-impaired`).
3. Ставим `sid` = лучшая по `MainSubtitleTags`, `secondary-sid` = лучшая по `SecondarySubtitleTags`.
4. Аудио: `aid` = лучшая по языковым тегам (порт `_englishKeywords`).

Формат `.ini` меняем на `settings.json`, при первом запуске мигрируем старый файл.

### 6.4 Отрезки: закладки + нарезка

**Модель закладки не меняется** (решение от 31.07.2026): закладка — это **точка**
во времени, ставится клавишей `T`, длительность фрагмента берётся из настроек панели.
Вариант с `,` / `.` для явного задания интервала начало–конец **отклонён**.

**Режим по умолчанию — перепаковка контейнера** (решение от 31.07.2026).
Видео и аудио копируются байт в байт, меняется только контейнер.
Ни одного перекодирования: нет потери качества, скорость в десятки раз выше реального времени.

> **Смена относительно v4.** Там `ReencodeAudioToAAC = true` по умолчанию,
> то есть фрагменты пережимались в H.264 + AAC. В v5 это уходит в необязательный
> запасной режим (см. «Когда перекодирование всё же нужно»).

**Процесс** (порт `BookmarksPanel::RecordNextFragment` + `VideoFragmentExtractor`):

1. Закладка = **точка** во времени. Отрезок = `[метка − buffer_secs, + duration_secs]`.
2. **Выравнивание по ключевому кадру.** Перед резкой запрашиваем у `ffprobe`
   ближайший ключевой кадр не позже запрошенного времени:
   ```
   ffprobe -v error -skip_frame nokey -select_streams v:0 \
           -show_entries frame=pkt_pts_time -read_intervals <t-15>%<t> -of csv=p=0 <файл>
   ```
   Берём последний результат ≤ `t` и режем ровно с него. Это даёт корректный
   первый кадр без чёрного экрана — та самая проблема, ради которой в v4
   включали перекодирование.
3. **Команда перепаковки:**
   ```
   ffmpeg -ss <keyframe_time> -i <вход> -t <длительность>
          -map 0:v:0 -map 0:a:<индекс>
          -c copy -avoid_negative_ts make_zero
          -movflags +faststart          # только для MP4
          <выход>
   ```
   - `-ss` **до** `-i` — быстрое позиционирование;
   - **никакого второго `-ss` после `-i`** — именно он при `-c copy` даёт
     отрицательные timestamps и чёрные кадры;
   - `-map 0:v:0` — только основной видеопоток, обложки игнорируются
     (исправление реального бага v4, сохраняем);
   - `-avoid_negative_ts make_zero` — сохраняем;
   - `-movflags +faststart` **по умолчанию не ставим** — он делает второй проход
     по готовому файлу ради веб-стриминга; для монтажа бесполезен. Отдельный флажок.
4. **Выбор контейнера.** Раз это перепаковка, контейнер обязан принять исходные кодеки:
   | Ситуация | Контейнер |
   |---|---|
   | Кодеки совместимы с MP4 (H.264/H.265/AV1 + AAC/MP3/AC3) | **`.mp4`** — как в v4, дружит с Adobe |
   | Всё остальное (DTS, TrueHD, PCM, FLAC, VP9 в MKV, ProRes) | **`.mkv`** — принимает почти всё |
   | Исходник `.mov` / ProRes | **`.mov`** |
   Определяем автоматически по `ffprobe` до запуска; пользователь может
   принудительно задать контейнер в настройках списка.
5. Имя файла — из `custom_name`, иначе `ЧЧММСС`; расширение по выбранному контейнеру;
   при коллизии `_01`, `_02`, …
6. Аудиодорожка — индекс текущей активной (в mpv это чище, чем `GetCurrentAudioTrackIndex`
   с обходом VLC-шного «Отключить/ID = −1»).
7. Прогресс: `-progress pipe:2`, парсим `out_time_ms=`, шлём в UI по каналу.

> **Длительность отрезка при перепаковке — приблизительная.** Проверено
> на этапе 4: заданные 5 секунд дают файл на 7,2 секунды. Причина в самой
> природе копирования потоков — обрезать посреди группы кадров нельзя,
> и хвост дописывается до её конца. У 4К HEVC группа длится около двух
> секунд, настолько же отрезок и удлиняется.
>
> Начало при этом точное: оно выровнено по опорному кадру, первый кадр
> полноценный. Кому нужна длительность секунда в секунду — включает
> перекодирование.

**Когда перекодирование всё же нужно** — отдельный флажок в настройках, по умолчанию выключен:
- нужен старт строго по указанной миллисекунде, а не по ключевому кадру;
- целевая программа не принимает исходный кодек;
- исходник с переменным fps, который ломает монтажную программу.

В этом режиме используется отработанная в v4 схема: двойной `-ss`
(грубый на −10 с до `-i`, точный после), `-c:v libx264 -preset ultrafast -crf 18`,
`-c:a aac -ac 2 -b:a 320k`. **Переносим дословно** — это выстраданное решение.

#### Оптимизация скорости нарезки

Помимо самой перепаковки, в обвязке v4 есть три источника потерь. Устраняем все.

| Что в v4 | Потеря | Решение в v5 |
|---|---|---|
| `ffprobe` исходного файла вызывается **на каждую закладку заново** (`VideoFragmentExtractor.cs:150`) — один и тот же файл парсится 20 раз | 0,3–0,5 с × N | Читаем один раз при открытии видео, кэшируем в состоянии приложения |
| Второй `ffprobe` для верификации результата (`VideoFragmentExtractor.cs:489`) | 0,3–0,5 с × N | Только по флагу отладки, вне горячего пути |
| Фрагменты режутся строго последовательно (`BookmarksPanel.cs:445`) | простой диска и CPU | ✅ сделано: общая очередь на 3 процесса, число берётся из настроек (`parallel_jobs`, ноль — по умолчанию) |
| Индекс ключевых кадров запрашивается на каждую метку | запуск процесса × N | ✅ сделано: один `ffprobe` со списком интервалов на весь пакет (`align_to_keyframes`) |

**Про параллелизм.** При перепаковке узкое место — диск, а не CPU.
На NVMe 3–4 параллельных процесса дают ×2–3; на HDD параллельность **вредит**
из-за перемещений головки. Значение вынесено в настройки (`parallel_jobs`),
ноль означает «по умолчанию» — три процесса. Тип носителя намеренно не
определяем: возня с WMI ради выбора между 1 и 3 не окупается, а поставить
единицу на HDD пользователь может сам.

**Ожидаемый результат** для пакета из 20 закладок по 30 с на 4К:

| | Время |
|---|---|
| v4, режим по умолчанию (перекодирование) | 10–20 минут |
| v5, перепаковка последовательно | ~20 с |
| v5, перепаковка + кэш ffprobe + параллелизм | **5–10 с** |

**Что сознательно не делаем.** Отказ от внешнего `ffmpeg.exe` в пользу
ремукса через `ffmpeg-next` прямо в процессе сэкономил бы ~150 мс на запуск
процесса (≈3 с на пакете из 20), но добавляет линковку FFmpeg в сборку,
тяжёлую зависимость и весь ремукс-код на себя. **Не окупается** — оставляем
внешний бинарник. К вопросу можно вернуться, если замеры покажут иное.

Запуск процессов — `tokio::process::Command`, UI не блокируется.

### 6.5 Именованные списки отрезков внутри видео (новое)

Речь **не о плейлистах файлов**, а о нескольких независимых наборах закладок
для одного и того же видео. Пример: для фильма отдельно ведутся списки
«Диалоги», «На вырезку», «Музыка» — каждый со своей длительностью фрагмента
и своей папкой сохранения.

**Модель данных** (`bookmarks.json`, версия 2):

```rust
struct BookmarksFile {
    version: u32,                        // = 2
    videos: Vec<VideoBookmarks>,
}

struct VideoBookmarks {
    video_file_name: String,             // ключ, как в v4 — имя без расширения
    active_list: String,                 // какой список сейчас выбран
    lists: Vec<BookmarkList>,
}

struct BookmarkList {
    name: String,
    duration_sec: u32,                   // длительность фрагмента для этого списка
    buffer_sec: u32,                     // отступ назад от метки
    output_dir: Option<PathBuf>,         // своя папка вывода; None — общая из настроек
    bookmarks: Vec<TimeBookmark>,
}

struct TimeBookmark { time_ms: i64, custom_name: Option<String> }
```

**Поведение:**
- Клавиша `T` добавляет закладку **в активный список**.
- Нарезка по кнопке REC режет активный список; отдельным пунктом — «нарезать все списки»
  (каждый в свою подпапку с именем списка).
- Переключение списка не трогает воспроизведение — меняется только содержимое панели
  и разметка меток на таймлайне.
- Метки на таймлайне красятся по списку, чтобы было видно принадлежность.
- **Отрезок будущего фрагмента подсвечивается на полосе жёлтым.** Видно не
  саму метку, а именно то, что вырежется: закладка на 15-й секунде при
  длительности 10 с даёт жёлтую область 15…25. С отступом отрезок сдвигается
  назад: метка 60 с, отступ 10 с, длительность 30 с → область 50…80.
  Отрисовка и расчёт готовы с этапа 1 (`ui/timeline.rs`, `FragmentRange`).

**Операции:** создать, переименовать, удалить, дублировать список,
перенести закладку в другой список, задать длительность/буфер/папку для списка.

**Как сделано (этап 5).** Переключатель списков — в шапке панели отрезков:
кружок цвета, выпадающий список и кнопка `⚙` с операциями. Список отрезков
продублирован в контекстном меню по правому щелчку. Создание и настройка —
одним диалогом (имя, длительность, отступ, папка); Enter сохраняет, Escape
закрывает, занятое или пустое имя остаётся в диалоге с пояснением. Перенос
закладки — правым щелчком по её строке. Имена сравниваются без учёта регистра
и краевых пробелов; последний список удалить нельзя. Кнопка «Вырезать все
списки» появляется, когда списков больше одного, и раскладывает отрезки по
подпапкам с именами списков.

**Совместимость:** плоский `bookmarks.json` из v4 читается и превращается в один
список с именем `Основной` — см. §6.10.

### 6.6 Позиции просмотра

Порт `WatchPositionManager` с сохранением всех правил:
- видео короче **5 минут** — не сохраняем;
- первые/последние **30 секунд** — не сохраняем (и удаляем старую запись);
- больше **95 %** просмотра — не предлагаем продолжить;
- ключ — хэш от **размера и даты изменения**, без пути и имени.

> **Уточнение после разбора кода v4.** Там ключ считается как
> `MD5(путь | размер | дата изменения)`, то есть переименование или
> перенос файла терял позицию просмотра. В v5 путь из ключа убран:
> тот же файл узнаётся после переименования и перемещения.
>
> Из-за смены схемы ключи пересчитываются при миграции: берём путь из
> записи v4 и считаем новый ключ по актуальным размеру и дате. Записи,
> чьих файлов уже нет на диске, пропускаем — они бесполезны и в v4
> (там позиция отбрасывалась той же проверкой существования файла).

Формат меняем с `.ini` на `watch_positions.json`, старый файл мигрируем при первом запуске.
Диалог «Продолжить просмотр» — порт `ContinueWatchingDialog`.

### 6.9 Форматы и 4К

mpv = FFmpeg, поэтому поддержка форматов **шире текущей**: MKV, MP4, AVI, MOV, WebM, TS, M2TS,

### 6.10 Миграция данных из v4 (обязательна)

Пользовательские данные из версии 4 переносятся **автоматически при первом запуске**.

| Файл v4 | Формат | Файл v5 | Состояние |
|---|---|---|---|
| `watch_positions.ini` | INI | `watch_positions.json` | ✅ **сделано на этапе 2.** Ключи пересчитываются по живому файлу; записи, чьих файлов нет, пропускаются |
| `bookmarks.json` | JSON (Newtonsoft) | `bookmarks.json` v2 | Этап 4: плоский список каждого видео → один `BookmarkList` с именем `Основной` |
| `subtitle_settings.ini` | INI | `settings.json` → `subtitle_priority` | Этап 3: теги основных/вторых субтитров, чёрный список, флаги |
| `settings.ini` | `ключ=значение` | `settings.json` | Этап 4: `RecordingPath` и параметры нарезки |

> Перенос каждого файла делается на том этапе, где появляется структура-приёмник:
> раскладывать данные некуда, пока нет кода, который их читает. Метка
> `migrated_from_v4` ставится один раз и закрывает весь перенос сразу, поэтому
> оставшиеся три файла подхватываются той же процедурой — она расширяется,
> а не запускается заново.

**Правила миграции:**
1. Ищем данные v4 в порядке: путь из аргумента `--import-from`, затем
   `C:\PITH\Source\Pith player\bin\x64\Debug\net6.0-windows`, затем рядом с v5.
   Не нашли — предлагаем указать папку вручную, но **не блокируем запуск**.
2. **Исходные файлы v4 не трогаем.** Только чтение. Старая версия должна
   продолжать работать после миграции.
3. Результат пишем атомарно (temp → `rename`), как требует §12.7.
4. Миграция одноразовая — отмечается файлом `migrated_from_v4` в каталоге данных.
   В нём хранится **номер выполненной стадии**: когда перенос расширяется,
   номер растёт и недостающее доделывается даже у тех, кто уже пользуется
   плеером. Простая отметка «выполнено» закрыла бы перенос навсегда.
5. Частичный сбой не фатален: не разобрался `subtitle_settings.ini` — переносим
   остальное, пишем предупреждение в лог и показываем итог пользователю.
6. Покрываем тестами на реальных файлах v4 — это требование §12.6.

**Где v5 хранит свои данные:** `%APPDATA%\PithPlayer\` — не теряется при переустановке
и не требует прав администратора. Если рядом с `.exe` лежит файл `portable.txt`,
данные хранятся рядом с программой (как в v4).

### 6.12 Окно подстраивается под соотношение сторон видео

Требование: **вертикальное видео открывается окном ровно своей формы** —
без чёрных полос по бокам, ширина и высота окна соответствуют кадру.
Горизонтальное и квадратное — по тому же правилу.

В v4 этого не было: окно оставалось горизонтальным, вертикальное видео
вписывалось в него с широкими чёрными полями, а `CheckAndFixVerticalVideo`
и `ResetVideoRenderer` боролись с последствиями. В v5 решаем в источнике.

**Подход — самый простой и безопасный из возможных** (решение от 31.07.2026).
Никакой сложной логики: одно действие при открытии файла, и любая нештатная
ситуация означает «ничего не делаем».

> **Проверено на этапе 0: вертикальное видео уже отображается правильно.**
> mpv вписывает кадр в окно с сохранением пропорций, ничего не растягивая.
> Пользователь подтвердил, что это работает отлично.
>
> Подгонка размера окна (§6.12) — **улучшение поверх исправного поведения**,
> а не исправление. Реализуя её, нельзя сломать то, что уже работает:
> если подгонка по любой причине не сработала, должно остаться нынешнее
> поведение — кадр вписан по пропорциям, с полями по краям.

**Алгоритм** — три шага, по событию `FILE_LOADED`:

1. Читаем `video-params/dw` и `video-params/dh` — отображаемые размеры кадра.
   > Именно `dw`/`dh`, а не `w`/`h`. Видео с телефона имеет в метаданных
   > `rotate=90`: сырые `w`/`h` покажут горизонтальный кадр, и вертикальное
   > видео снова откроется лёжа. `dw`/`dh` отдают размеры с уже применённым
   > поворотом и пиксельным соотношением.
2. Вписываем в рабочую область текущего монитора (запас 10 %), сохраняя пропорции.
   Только уменьшаем, никогда не увеличиваем.
3. Задаём размер окна и центрируем.

**Правило безопасности — во всех перечисленных случаях просто не трогаем окно:**

- не удалось прочитать `dw`/`dh`, либо значения нулевые или абсурдные;
- сейчас полноэкранный режим или окно развёрнуто;
- пользователь уже менял размер окна вручную в текущем сеансе;
- аудиофайл без видеопотока.

Во всех этих случаях mpv сам вписывает кадр в имеющееся окно с чёрными полями —
поведение корректное, просто не идеальное. **Отсутствие подгонки не является ошибкой.**

**Настройка одна:** `fit_to_video` в `settings.json`, по умолчанию `true`.
Выключается, если мешает.

Сознательно **не делаем**: `min_inner_size` по соотношению сторон (мешает ручному
ресайзу), увеличение мелкого видео (растянутое мыло), подгонку при каждой смене
дорожки или размера кадра по ходу воспроизведения.

## 10. Первые шаги (этап 0, по пунктам)

1. Установить Rust (`rustup`, toolchain `stable-x86_64-pc-windows-msvc`).
2. Скачать `mpv-dev-x86_64-*.7z` (shinchiro), распаковать в `third_party/mpv/`

3. `cargo new --lib` для крейтов, собрать workspace.
4. Прописать `MPV_SOURCE` в `.cargo/config.toml` — чтобы сборка была воспроизводимой.
5. Минимальный `main.rs`: окно eframe + mpv render context + `loadfile` из аргумента.
6. **Замеры** на реальных 4К-файлах: время старта, seek, CPU/GPU в трёх режимах hwdec.
7. Зафиксировать результат замеров в этом документе — и только потом наращивать UI.
8. `git init`, первый коммит.

## 12. Правила разработки

Обязательны к соблюдению на всех этапах. Цель — приложение, которое можно
дорабатывать годами, не утонув в собственном коде (главная болезнь v4).

### 12.1 Язык

- **Все ответы, объяснения и обсуждения — только на русском.**
- Комментарии в коде — на русском.
- Идентификаторы, имена файлов, модулей и веток — на английском.
- Сообщения коммитов — на русском.

### 12.2 Размер файлов — строгий контроль

- **Файл исходного кода — не более 400 строк.** Это жёсткий предел, а не пожелание.
- Файл дорос до 400 — разбиваем **немедленно**, а не «когда-нибудь потом».
- При приближении к 350 строкам заранее продумываем разделение по ответственности.
- Функция — не более 50 строк. Вложенность — не более 3 уровней.
- **Исключения:** `PLAN.md` и прочая документация, автогенерируемые файлы.

Проверка перед каждым коммитом:

```bash
find crates -name "*.rs" -exec wc -l {} + | awk '$1 > 400 {print "ПРЕВЫШЕНИЕ:", $2, $1}'
```

> Урок v4: `DraggableSecondarySubtitleOverlay.cs` — 2 725 строк,
> `MainForm` разбит на 7 partial-файлов по 5 000 строк суммарно.
> Такой код невозможно ни читать, ни менять безопасно.

### 12.3 Надёжность — плеер не имеет права падать

- **Никаких `unwrap()` и `expect()` в рабочем коде.** Только `Result` +
  `thiserror` для библиотечных крейтов, `anyhow` — в `pith-app`.
  В тестах `unwrap()` разрешён.
- Битый файл, отсутствующий кодек, недоступный диск — это **сообщение пользователю**,
  а не аварийное завершение.
- **Мягкая деградация:** нет `ffmpeg.exe` — нарезка отрезков отключена,
  всё остальное работает. Нет `libmpv.dll` — понятное сообщение вместо тихого падения.
- Паника логируется через `panic::set_hook` с записью в файл и показом диалога.

### 12.4 Архитектура — границы соблюдаются

- Зависимости строго в одну сторону:
  `pith-store` ← `pith-mpv` / `pith-subs` / `pith-fragments` ← `pith-app`.
- **UI никогда не обращается к libmpv напрямую** — только через API `pith-mpv`.
- **Состояние приложения живёт в одном месте** (`app.rs`), а не размазано по компонентам UI.
- **Никаких таймеров-опросов.** Только события mpv и `observe_property`.
  Появление в коде «подождать 800 мс и попробовать ещё раз» — признак ошибки проектирования.
- Все блокирующие операции (FFmpeg, чтение больших файлов, парсинг) — вне UI-потока.

### 12.5 Гигиена кода

- **Мёртвый код удаляем, а не комментируем.** История есть в git.
  В v4 накопилось ~2 000 строк закомментированной диагностики.
- **Никаких магических чисел** — именованные константы вверху модуля
  (`MIN_VIDEO_DURATION_MS`, `SEEK_STEP_SEC`, `MAX_SUBTITLE_SIZE`).
- **`println!` / `dbg!` запрещены** — только `tracing` с уровнями.
- Перед каждым коммитом обязательно:

```bash
cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test
```

### 12.6 Тесты

Тестируем **чистую логику**, UI не тестируем:

- парсеры SRT / ASS / VTT (включая битые и нестандартные файлы);
- расчёт приоритета дорожек по тегам;
- правила сохранения позиций просмотра (5 мин / 30 с / 95 %);
- сборку команд FFmpeg — сравнением строк, без реального запуска;
- сериализацию и миграции JSON.

**Каждое исправленное падение или баг закрывается тестом**, чтобы не вернулось.

### 12.7 Данные пользователя неприкосновенны

- В каждом JSON — поле `version`.
- Миграции только вперёд и без потерь; старый файл сохраняется как `.bak`.
- **Атомарная запись:** пишем во временный файл, затем `rename`.
  Закладки не должны теряться при сбое питания или падении.
- Формат никогда не ломаем молча.

### 12.8 Процесс

- **Каждый этап заканчивается работающим приложением.** `main` всегда собирается и запускается.
- Коммиты маленькие и осмысленные — один коммит решает одну задачу.
- Новая зависимость добавляется только с обоснованием: что даёт и почему
  нельзя обойтись стандартной библиотекой.
- Оптимизация — только после замера. Сначала цифры, потом правки.
- **Каждый этап завершается чек-листом ручной проверки для пользователя** (раздел 13).
  Этап не считается закрытым, пока чек-лист не пройден.

### Чего проверка не покрывает

Клавиатурный и мышиный ввод из сценариев доходит до окна плеера
ненадёжно: `SendKeys` не доставляет буквы, скобки и стрелки, а снимок
экрана несколько раз отдавал устаревший кадр либо чужие окна поверх.

Что помогло и заложено в `scripts\lists_test.ps1` и `scripts\robustness_test.ps1`:

- клавиши слать через `keybd_event` **со скан-кодом** — winit смотрит
  на физическое положение клавиши;
- перед вводом щёлкнуть по видео: иначе фокус остаётся у системных
  всплывающих окон;
- между нажатием и отпусканием кнопки мыши держать паузу — мгновенный
  щелчок egui иногда не засчитывает;
- **снимать окно через `PrintWindow` с `PW_RENDERFULLCONTENT`**, а не копией
  экрана. Копия экрана отстаёт на секунду-другую и показывает состояние
  до нажатия — из-за этого рабочие диалоги выглядели неоткрывшимися;
- между запусками плеера выдерживать паузу: порт защиты от второго запуска
  освобождается не мгновенно, и новый экземпляр молча закрывается.

Поэтому проверены автоматически: разбор данных, сборка команд, правила
отбора, расчёты — всё, что покрывается тестами. Проверено вручную через
запуск и снимки: воспроизведение, дорожки, субтитры, поиск, нарезка.
Остальное — на живой проверке пользователем, и это отражено в чек-листах
раздела 13.
